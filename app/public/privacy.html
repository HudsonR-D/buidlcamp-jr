Privacy and data flow

Last updated: 2026-09-16.

Core learning

BuidlCamp does not require a learner account. A nickname, age band, reading preference, learning evidence, projects, practice drafts/responses, and educator records are stored in this browser. The optional adult-controls PIN is salted and hashed locally. It is a convenience barrier, not identity verification, access control against another device user, or verified parental consent. No advertising or application analytics are included.

Local autosave uses browser storage. IndexedDB checkpoint history retains up to 20 versions per project within 50 MB total and removes older versions when necessary. Browser clearing, storage pressure, device loss, or private-browsing behavior can remove work. Export copies you need to keep.

Optional GitHub checkpoints

Eligible users connect their own GitHub account to a GitHub App and choose a dedicated private repository with selected-repository access. Ages 10–12 use local exercises and exports; an adult may separately upload a reviewed export with their own account. Personal logins must not be shared.

Each save previews project source, project metadata (ID, name, template, timestamp, reflection, checklist), commit message, and explicitly checked milestone evidence. Those fields go through the BuidlCamp Worker to GitHub. We do not upload age bands, PINs, AI conversations, educator reviews, credentials, or full workspace backups through the checkpoint endpoint. Do not place personal information or secrets inside project code, names, reflections, messages, or evidence. Pattern scanning cannot recognize every secret. GitHub receives the account identity and repository activity associated with a commit.

Only buidlcamp/projects/<project-id>/index.html and checkpoint.json are managed. Unrelated files are preserved. Repositories must remain private and writable. Private does not hide data from GitHub or invited collaborators. Git history retains previous versions even after files are changed or deleted.

Integration sessions

GitHub authorization uses state and PKCE. Expiring GitHub access tokens are encrypted on the server; refresh tokens are discarded. The browser receives an opaque Secure, HttpOnly, SameSite cookie and an in-memory CSRF token. Sessions expire within eight hours and require reconnection. D1 stores encrypted integration tokens, session identifiers, GitHub ID/login, role acknowledgment, authorization-flow state, and rate-limit counters. It does not store learner projects, AI conversations, or provider API keys. Expired rows are cleaned hourly. Provider backups may retain deleted rows under the hosting provider's retention and recovery policies.

Disconnect invalidates the local hosted session and attempts to revoke that app authorization at GitHub. GitHub revocation webhooks invalidate related sessions; repository operations also check authorization live. A lost connection can prevent remote revocation. You can revoke app access directly in GitHub settings.

Optional AI

Subscription handoffs open the provider's own app. Nothing is sent there automatically: choose what prompt to copy and paste. Subscription access does not include API billing.

The hosted relay requires an authenticated adult-role session plus explicit adult acknowledgment. That statement is self-declared, not verified age or parental consent. An adult's provider key and prompt travel over HTTPS through the Worker to the selected fixed OpenAI or Anthropic endpoint. Keys remain in browser/request memory and clear from the interface when adult controls lock, provider/mode changes, or the page closes. The relay does not persist keys or request/response bodies and has no application body logging. Prompt drafts and returned responses may be saved in the local practice workspace; the provider applies its own retention and billing terms. A cancellation stops local waiting and asks transport to abort; upstream processing or charges may already have occurred.

Files and deletion

Full workspace backups include local learning/practice and educator data, but exclude the PIN and API keys. Portfolios include the nickname, lesson evidence, projects, and a submission identifier; they omit age, practice conversations, adult settings, and unrelated educator records. Educator feedback files include only feedback and referenced submission/lesson/project identifiers. Files are ordinary documents, not authenticated grades; share them deliberately.

Workspace deletion clears current and legacy learning records and local checkpoint history, and disconnects the hosted session when reachable. Appearance preference and cached public app assets can remain. Downloaded files, files held by educators, GitHub commits, and provider records are outside that deletion. Remove those copies through their respective services. On a shared device, use separate browser profiles and disconnect before handing the device to someone else.

Hosting metadata

Cloudflare serves this site and processes ordinary connection metadata such as IP addresses, request URLs, timestamps, and browser information. Infrastructure security, request accounting, and network-error reporting can exist even though BuidlCamp application analytics and Worker observability logs are disabled. GitHub and AI providers process data under their own policies. BuidlCamp bundles no external fonts or analytics scripts. Cloudflare may inject same-origin bot-detection code into delivered HTML and use security cookies under its own policies.

Questions and privacy-related defects can be raised through the repository's private security reporting channel. Do not post learner information or credentials in a public issue.
